# 高并发场景实现详解

## 概述

本文档详细说明七云菜馆项目中三大高并发场景的技术实现：
1. **Redis + Lua 脚本实现原子性库存扣减**（防止超卖）
2. **RabbitMQ 实现流量削峰填谷**（异步消息处理）
3. **乐观锁机制处理并发冲突**（订单支付与超时关单）

---

## 一、Redis + Lua 脚本：原子性库存扣减

### 1.1 核心问题
在秒杀场景下，多个用户同时抢购同一商品，如果不加控制会导致：
- **超卖问题**：库存为 10，但卖出了 15 件
- **并发冲突**：多个请求同时读取库存，都认为有货

### 1.2 解决方案
使用 Redis + Lua 脚本实现原子性库存扣减，保证：
- **原子性**：Lua 脚本在 Redis 中以原子方式执行
- **高性能**：Redis 内存操作，QPS 可达 10 万+
- **防超卖**：先检查库存，再扣减，整个过程不可分割

### 1.3 代码实现

**文件位置**：`restaurant-server/src/main/java/com/qiyun/restaurant/service/impl/SeckillServiceImpl.java`

```java
/**
 * Lua 脚本：原子性库存扣减
 * 逻辑：
 * 1. 检查库存是否充足
 * 2. 如果充足，扣减库存并返回成功
 * 3. 如果不足，返回失败
 */
private static final String STOCK_DEDUCT_SCRIPT =
        "local stock = redis.call('get', KEYS[1]) " +
        "if not stock then " +
        "    return -1 " +  // 库存不存在
        "end " +
        "if tonumber(stock) < tonumber(ARGV[1]) then " +
        "    return 0 " +   // 库存不足
        "end " +
        "redis.call('decrby', KEYS[1], ARGV[1]) " +
        "return 1";         // 扣减成功

@Override
public boolean deductStock(Long dishId, Integer quantity) {
    String stockKey = STOCK_KEY_PREFIX + dishId;
    
    try {
        // 执行 Lua 脚本
        Long result = redisTemplate.execute(
            new DefaultRedisScript<>(STOCK_DEDUCT_SCRIPT, Long.class),
            Collections.singletonList(stockKey),
            quantity.toString()
        );
        
        if (result == null || result == -1) {
            log.error("库存不存在: dishId={}", dishId);
            return false;
        }
        
        if (result == 0) {
            log.warn("库存不足: dishId={}, quantity={}", dishId, quantity);
            return false;
        }
        
        log.info("库存扣减成功: dishId={}, quantity={}", dishId, quantity);
        return true;
        
    } catch (Exception e) {
        log.error("库存扣减失败: dishId={}", dishId, e);
        return false;
    }
}
```

### 1.4 面试要点

**Q1: 为什么使用 Lua 脚本而不是分布式锁？**

- **性能优势**：Lua 脚本原子执行，无需加锁，性能更高
- **简单可靠**：不需要考虑锁的获取、释放、超时等问题
- **避免死锁**：没有锁竞争，不会出现死锁

**Q2: Lua 脚本的原子性是如何保证的？**
- Redis 单线程模型，Lua 脚本执行期间不会被其他命令打断
- 整个脚本作为一个原子操作执行

**Q3: 如果 Redis 宕机怎么办？**
- 使用 Redis 主从复制 + 哨兵模式保证高可用
- 库存数据持久化到 MySQL，Redis 重启后从 MySQL 加载
- 秒杀开始前预热库存到 Redis

## 二、分布式限流：令牌桶算法 + Lua 脚本

### 2.1 核心问题
秒杀瞬间流量激增，需要限流保护后端服务：
- **流量洪峰**：瞬间 10 万 QPS 冲击服务器
- **服务雪崩**：后端服务被打垮，影响其他业务

### 2.2 解决方案
使用令牌桶算法 + Redis + Lua 脚本实现分布式限流：
- **令牌桶算法**：平滑限流，允许一定程度的突发流量
- **分布式**：多个服务实例共享限流配置
- **高性能**：Redis 内存操作，延迟低

### 2.3 代码实现

**文件位置**：`restaurant-server/src/main/java/com/qiyun/restaurant/utils/RateLimiterUtil.java`

```java
/**
 * Lua 脚本：令牌桶限流算法
 * 参数：
 * KEYS[1]: 令牌桶的 key
 * ARGV[1]: 令牌桶容量（最大令牌数）
 * ARGV[2]: 令牌生成速率（每秒生成的令牌数）
 * ARGV[3]: 当前时间戳（秒）
 * ARGV[4]: 本次请求需要的令牌数
 */
private static final String RATE_LIMITER_SCRIPT =
        "local key = KEYS[1] " +
        "local capacity = tonumber(ARGV[1]) " +
        "local rate = tonumber(ARGV[2]) " +
        "local now = tonumber(ARGV[3]) " +
        "local requested = tonumber(ARGV[4]) " +
        
        // 获取当前令牌数和上次更新时间
        "local bucket = redis.call('hmget', key, 'tokens', 'last_time') " +
        "local tokens = tonumber(bucket[1]) or capacity " +
        "local last_time = tonumber(bucket[2]) or now " +
        
        // 计算新增令牌数
        "local delta = math.max(0, now - last_time) " +
        "local new_tokens = math.min(capacity, tokens + delta * rate) " +
        
        // 判断令牌是否充足
        "if new_tokens >= requested then " +
        "    new_tokens = new_tokens - requested " +
        "    redis.call('hmset', key, 'tokens', new_tokens, 'last_time', now) " +
        "    redis.call('expire', key, 3600) " +
        "    return 1 " +  // 允许通过
        "else " +
        "    return 0 " +  // 拒绝请求
        "end";

public static boolean tryAcquire(String key, int capacity, int rate, int permits) {
    try {
        Long result = redisTemplate.execute(
            new DefaultRedisScript<>(RATE_LIMITER_SCRIPT, Long.class),
            Collections.singletonList(RATE_LIMITER_PREFIX + key),
            String.valueOf(capacity),
            String.valueOf(rate),
            String.valueOf(System.currentTimeMillis() / 1000),
            String.valueOf(permits)
        );
        
        return result != null && result == 1;
        
    } catch (Exception e) {
        log.error("限流检查失败: key={}", key, e);
        // 限流失败时，默认拒绝请求（fail-close）
        return false;
    }
}
```

### 2.5 面试要点

**Q1: 为什么选择令牌桶而不是漏桶算法？**
- **令牌桶**：允许一定程度的突发流量，用户体验更好
- **漏桶**：严格限制流量速率，过于死板

**Q2: 如何设置令牌桶参数？**
- **容量（capacity）**：设置为速率的 2 倍，允许短时突发
- **速率（rate）**：根据后端服务承载能力设置
- 例如：后端 QPS 1000，设置 capacity=2000, rate=1000

**Q3: 限流失败后如何处理？**
- 返回友好提示："系统繁忙，请稍后再试"
- 前端可以实现重试机制（指数退避）
- 记录限流日志，用于容量规划

## 三、RabbitMQ：流量削峰填谷

### 3.1 核心问题
秒杀场景下，订单创建是同步操作，会导致：
- **响应慢**：用户等待时间长，体验差
- **数据库压力大**：瞬间大量写入，数据库扛不住
- **服务阻塞**：同步处理阻塞线程，降低吞吐量

### 3.2 解决方案
使用 RabbitMQ 将同步下单流程改为异步消息处理：
- **削峰**：将瞬时流量分散到一段时间内处理
- **解耦**：订单创建和后续处理解耦，提高系统弹性
- **提升吞吐**：异步处理，不阻塞用户请求

### 3.3 架构设计

```
用户请求 → 订单服务（快速响应）→ RabbitMQ → 消费者（异步处理）
   ↓                                      ↓
返回"排队中"                          处理订单逻辑
                                         ↓
                                    通知用户结果
```

```java
@RabbitListener(queues = RabbitMQConfig.ORDER_CREATE_QUEUE)
public void handleOrderCreate(Order order, Message message, Channel channel) throws IOException {
    String messageId = message.getMessageProperties().getMessageId();
    long deliveryTag = message.getMessageProperties().getDeliveryTag();
    
    log.info("接收到订单创建消息: orderId={}, messageId={}", order.getId(), messageId);
    
    try {
        // 幂等性检查
        if (!checkIdempotent(messageId)) {
            log.warn("消息已被消费，跳过: messageId={}", messageId);
            channel.basicAck(deliveryTag, false);
            return;
        }
        
        // 处理业务逻辑
        orderService.processOrderCreate(order);
        
        // 手动 ACK 确认
        channel.basicAck(deliveryTag, false);
        log.info("订单创建消息处理成功: orderId={}, messageId={}", order.getId(), messageId);
        
    } catch (Exception e) {
        log.error("订单创建消息处理失败: orderId={}, messageId={}", 
            order.getId(), messageId, e);
        
        // 处理失败，根据重试次数决定是否重新入队
        handleMessageFailure(message, channel, deliveryTag, e);
    }
}
```

### 3.7 幂等性保证

```java
/**
 * 幂等性检查
 * 使用 Redis 的 SETNX 命令实现
 */
private boolean checkIdempotent(String messageId) {
    String idempotentKey = "order:consumed:" + messageId;
    
    // 使用 SETNX 命令，如果 key 不存在则设置成功返回 true，存在则返回 false
    Boolean result = redisTemplate.opsForValue()
        .setIfAbsent(idempotentKey, "1", 24, TimeUnit.HOURS);
    
    return Boolean.TRUE.equals(result);
}
```

### 3.8 消息重试机制

```java
/**
 * 处理消息失败
 * 根据重试次数决定是否重新入队或进入死信队列
 */
private void handleMessageFailure(Message message, Channel channel, 
                                  long deliveryTag, Exception exception) throws IOException {
    // 获取重试次数
    Integer retryCount = (Integer) message.getMessageProperties()
        .getHeaders().getOrDefault("x-retry-count", 0);
    
    // 最大重试次数
    final int MAX_RETRY_COUNT = 3;
    
    if (retryCount < MAX_RETRY_COUNT) {
        // 重新入队，等待重试
        log.warn("消息处理失败，重新入队: messageId={}, retryCount={}", 
            message.getMessageProperties().getMessageId(), retryCount);
        
        // 增加重试次数
        message.getMessageProperties().getHeaders().put("x-retry-count", retryCount + 1);
        
        // NACK 并重新入队
        channel.basicNack(deliveryTag, false, true);
        
    } else {
        // 超过最大重试次数，进入死信队列
        log.error("消息处理失败，超过最大重试次数，进入死信队列: messageId={}, retryCount={}", 
            message.getMessageProperties().getMessageId(), retryCount);
        
        // NACK 但不重新入队，消息会进入死信队列
        channel.basicNack(deliveryTag, false, false);
    }
}
```

### 3.10 面试要点

**Q1: 为什么使用 RabbitMQ 而不是 Kafka？**
- **RabbitMQ**：支持消息确认、死信队列、延迟队列，适合订单场景
- **Kafka**：高吞吐量，适合日志、监控等场景

**Q2: 如何保证消息不丢失？**
- **生产者确认**：使用 publisher confirms 机制
- **消息持久化**：队列和消息都设置为持久化
- **消费者确认**：手动 ACK，处理成功后才确认

**Q3: 如何保证消息不重复消费？**
- **幂等性检查**：使用 Redis SETNX 记录已消费的消息 ID
- **业务幂等**：订单创建时检查订单是否已存在

**Q4: 死信队列的作用是什么？**
- 存储处理失败的消息，避免消息丢失
- 可以人工介入处理异常消息
- 可以分析失败原因，优化系统

## 四、乐观锁：处理并发冲突

### 4.1 核心问题
订单支付和超时关单可能同时发生，导致：
- **并发冲突**：支付成功的订单被关闭
- **数据不一致**：订单状态混乱

### 4.2 解决方案
使用 MyBatis Plus 的乐观锁机制：
- **版本号**：每次更新时检查版本号是否一致
- **无锁设计**：不需要加锁，性能高
- **自动重试**：MyBatis Plus 自动处理版本号更新

### 4.7 乐观锁工作原理

```sql
-- 原始 SQL（没有乐观锁）
UPDATE orders SET status = 5 WHERE id = 123;

-- 乐观锁 SQL（MyBatis Plus 自动生成）
UPDATE orders 
SET status = 5, version = version + 1 
WHERE id = 123 AND version = 1;

-- 如果 version 已经变化（被其他事务修改），WHERE 条件不满足，更新失败
```

### 4.8 面试要点

**Q1: 乐观锁和悲观锁的区别？**
- **乐观锁**：假设不会发生冲突，更新时检查版本号，适合读多写少
- **悲观锁**：假设会发生冲突，先加锁再操作，适合写多读少

**Q2: 乐观锁失败后如何处理？**
- **重试**：可以重试 3 次，每次重新查询最新数据
- **返回失败**：告知用户操作失败，让用户重新操作
- **记录日志**：记录冲突日志，用于分析优化

**Q3: 为什么订单场景适合用乐观锁？**
- **冲突概率低**：支付和关单同时发生的概率很低
- **性能好**：不需要加锁，不会阻塞其他操作
- **简单**：MyBatis Plus 自动处理，代码简洁

**Q4: 乐观锁的版本号会溢出吗？**
- 使用 Integer 类型，最大值 21 亿
- 一个订单不会更新这么多次，不用担心溢出
- 如果担心，可以使用 Long 类型

### 5.2 代码示例

```java
@PostMapping("/seckill")
public Result<String> seckill(@RequestBody SeckillRequest request) {
    Long dishId = request.getDishId();
    Integer quantity = request.getQuantity();
    Long userId = request.getUserId();
    
    // 1. 限流检查
    if (!RateLimiterUtil.tryAcquire("seckill:dish:" + dishId, 2000, 1000, 1)) {
        return Result.error("系统繁忙，请稍后再试");
    }
    
    // 2. 扣减库存
    boolean stockSuccess = seckillService.deductStock(dishId, quantity);
    if (!stockSuccess) {
        return Result.error("库存不足");
    }
    
    try {
        // 3. 创建订单（快速创建，不做复杂处理）
        Order order = new Order();
        order.setUserId(userId);
        order.setDishId(dishId);
        order.setQuantity(quantity);
        order.setStatus(0); // 0=待支付
        orderService.save(order);
        
        // 4. 发送消息到 RabbitMQ
        String messageId = orderMessageProducer.sendOrderCreateMessage(order);
        
        // 5. 返回"排队中"给用户
        return Result.success("订单创建中，请稍后查看订单状态");
        
    } catch (Exception e) {
        // 失败时恢复库存
        seckillService.restoreStock(dishId, quantity);
        log.error("秒杀下单失败: dishId={}, userId={}", dishId, userId, e);
        return Result.error("下单失败，请重试");
    }
}
```
