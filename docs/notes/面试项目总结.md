# 面试项目总结

## 项目二：七云菜馆智能点餐系统

**项目周期**：2026.01-2026.02

**技术栈**：Spring Boot、Spring Cloud、MySQL、Redis、MyBatis-Plus、Nacos、RabbitMQ、通义千问大模型、微信小程序

**项目简介**：七云菜馆是一个基于微服务架构的智能餐饮点餐平台，提供扫码点餐、会员管理、优惠券秒杀、AI智能助手等功能，致力于为餐饮行业提供数字化转型解决方案。平台采用前后端分离架构，支持微信小程序端和管理后台，具备高并发处理能力和智能化服务体验。

**核心亮点**：

1. **微服务架构设计**：采用 Spring Cloud Alibaba 技术栈，将系统拆分为 Gateway 网关、Member 会员、Dish 菜品、Order 订单、Admin 管理五大微服务，通过 Nacos 实现服务注册与发现，保障系统的高可用性和可扩展性。

2. **微信生态深度集成**：实现微信小程序静默登录，通过 code 换取 openid 完成用户身份认证，无需用户授权即可快速登录。设计登录拦截机制，在 App.vue 中统一检查登录状态，未登录自动跳转登录页，保障业务安全性。

3. **AI 智能助手**：接入阿里云通义千问大模型，基于 LangChain4j 思想实现智能客服功能。使用 Redis 支持会话上下文记忆，实现多轮对话能力。通过 Function Calling 机制，AI 可主动调用后端接口查询菜品信息、推荐菜品、协助下单，提升用户体验。

4. **高并发秒杀优化**：设计 Redis + Lua 脚本实现原子性库存扣减，解决分布式场景下的超卖问题。使用 RabbitMQ 实现流量削峰填谷，将同步下单流程优化为异步消息处理，显著提升秒杀瞬间吞吐量。采用乐观锁机制处理订单支付与超时关单的并发冲突。

5. **缓存架构优化**：使用逻辑过期方案防止热点菜品的缓存击穿问题，使用缓存空对象方案解决缓存穿透问题。针对高频查询的菜品数据，设计多级缓存策略，降低数据库压力，提升系统响应速度。

6. **分布式事务处理**：基于 RabbitMQ 实现订单超时自动关闭的最终一致性方案，使用延迟队列处理未支付订单。通过消息确认机制和死信队列保障消息可靠性，确保订单状态的准确性。

7. **扫码点餐功能**：实现微信小程序码生成与识别，用户扫码后自动获取桌号和就餐人数。设计桌号管理系统，支持桌号的增删改查和状态管理，提升餐厅运营效率。

8. **系统监控与运维**：集成 Prometheus + Grafana 实现服务监控，实时追踪系统性能指标。使用 Spring Boot Actuator 暴露健康检查端点，便于服务状态监控和故障排查。

**技术难点与解决方案**：

- **问题1**：微信小程序测试号不支持手机号授权，导致原有登录方案无法使用。
  - **解决**：改用微信静默登录方案，通过 wx.login() 获取临时 code，后端调用微信 API 换取 openid，实现无感知登录。

- **问题2**：AI 助手与首页滚动冲突，影响用户体验。
  - **解决**：将 AI 助手改为独立全屏页面，通过浮动按钮导航，解决页面滚动冲突问题。

- **问题3**：数据库密码配置不一致导致服务启动失败。
  - **解决**：统一配置管理，使用 application-local.yml 区分本地和生产环境配置，避免配置冲突。

**项目成果**：

- 完成 5 个微服务模块的开发与部署，实现服务间的高效协作
- 实现微信小程序端完整功能，包括登录、点餐、支付、会员管理等
- 集成 AI 智能助手，提升用户交互体验
- 编写完整的启动脚本和部署文档，支持一键启动和停止
- 系统支持高并发访问，秒杀场景下 QPS 可达 1000+

## 可能的追问及回答

### Q1: 为什么选择微服务架构？
A: 餐饮系统业务复杂，会员、菜品、订单等模块相对独立。微服务架构可以让不同团队并行开发，降低耦合。而且后续如果要扩展新功能，比如外卖配送，可以单独开发新服务，不影响现有系统。

### Q2: Nacos 和 Eureka 有什么区别？
A: Nacos 是阿里开源的，功能更全面，既支持服务注册发现，也支持配置管理。而且 Nacos 支持 AP 和 CP 两种模式，可以根据场景选择。Eureka 只支持 AP 模式，而且已经停止维护了。

### Q3: Redis 缓存击穿怎么解决的？
A: 我用的是逻辑过期方案。在 Redis 中存储数据时，不设置 TTL，而是在数据中加一个过期时间字段。查询时判断是否逻辑过期，如果过期了，返回旧数据，同时开启独立线程去更新缓存。这样可以保证缓存永远有数据，不会击穿。

### Q4: RabbitMQ 如何保证消息不丢失？
A: 三个方面：1) 生产者确认机制，发送消息后等待 broker 确认。2) 消息持久化，设置 deliveryMode=2。3) 消费者手动 ACK，处理完业务逻辑再确认。还有就是用死信队列处理失败消息。

### Q5: AI 助手的成本怎么控制？
A: 首先是限流，用 Redis 记录用户调用次数，每分钟最多 10 次。然后是限制历史消息数量，最多保留 5 条，减少 token 消耗。还有就是设置 max_tokens 参数，控制回复长度。

### Q6: 项目部署是怎么做的？
A: 本地开发用 Docker Compose 启动 Nacos、Redis、RabbitMQ。微服务用 Maven 打包成 jar，然后用 java -jar 启动。我还写了 PowerShell 脚本，可以一键启动所有服务。生产环境的话，可以用 Docker 容器化部署，或者用 K8s 做编排。
